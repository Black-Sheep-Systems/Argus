Argus User Guide

Argus is a desktop app for running a Linux server from your PC. This guide covers every page, card and button: what you see, what happens on the server when you press it, what Argus refuses to do, and the commands to do the same job by hand when Argus isn't available.

Labels in bold are exactly as they appear on screen. Words in angle brackets, such as <name> or <stamp>, are placeholders: replace them, brackets included, before you run a command. Nothing secret is written here: secret files are named by path only.

Placeholders such as <server address> and <your user> stand for your own server's detailsWritten 2 November 2026 from the Argus source

How Argus Works

What Argus is

A Windows desktop app (Electron screen, Rust native module, app/ and native/ and core/) for administering one Linux server over one SSH connection. The sidebar shows "Argus" and the server's name, which is set in the source. Only one copy of Argus can run at a time; starting a second one brings the first window forward (app.requestSingleInstanceLock).

How it connects (sign-in screen: "Sign In to the Server")

  • These details are compiled into Argus: to use it with your own server, change them in the source (native/src/lib.rs, core/src/bin/signin_check.rs, app/main.js, and SERVER_IP in server/argus-helper) and rebuild. Names such as bss-caddy, bss-php and /opt/web are the container and folder names on the server Argus was built for; yours may differ.
  • Target is hard-coded in native/src/lib.rs (the sign-in messages quoted below are in core/src/lib.rs): host <server address> (the server), port 22, user <your user>. The screen says "Signing in as <your user>@<server address>."
  • Key file: %USERPROFILE%\.ssh\<your key file> on the PC (falls back to $HOME). If it is missing: "no key file at ...".
  • Step 1, field Key passphrase, button Continue: the key is unlocked on the PC, Argus connects and checks the server's host key against the pinned fingerprint (built into Argus). Any other key, or a certificate instead of a plain key, is refused ("server key did not match the pinned key: server showed ..., expected ..."). The key is then presented.
    • If the server lets the key in without asking for a code, Argus refuses: "the server let the key in without asking for the authenticator code; two-factor is not being enforced".
    • If the key is accepted but no keyboard-interactive step is offered: "key accepted, but the server is not offering the authenticator step".
  • Step 2, text "Key accepted. Now the code from your authenticator app.", field Authenticator code (6 to 8 digits), button Sign In. A wrong code ends the attempt and the screen goes back to the passphrase ("... Start again with your passphrase."). Argus answers at most one prompt and stops after four rounds.
  • Time limits: connecting and each sign-in step 20 s; each server command 60 s; keepalive every 30 s; the connection closes after 600 s of inactivity.
  • Once in, the header shows the pill Connected and "<your user>@<server address> · key and code · server key matched".
  • If the connection drops, the pill becomes Not connected and the message says "Lost the connection: ... Disconnect and sign in again (a fresh code is needed)."
  • README limits: the passphrase and code pass through JavaScript strings that cannot be wiped; russh keeps one plain copy of the code; a Disconnect pressed during sign-in does not cancel the sign-in under way.

What runs where

On the PC:

  • The window (renderer) can call only the fixed list in app/preload.js. It loads nothing from the network: every request that is not one of Argus's own screen files is cancelled, and camera, microphone and similar permissions are refused.
  • main.js does the PC-side work: listing PC folders and drives, PC file previews, the Hephaestus git commands (repository hard-coded as <path to the Hephaestus repository>), the public DNS lookups for the mail record check, opening https://<mail server address>/admin in the browser, and the clipboard (sensitive copies are cleared after 30 s if unchanged; Windows clipboard history may still keep a copy).
  • The native module holds the only SSH connection, and allows only the helper actions in its ACTIONS list (plus SECRET_ACTIONS, which take a password on stdin). Every argument must be 1 to 2048 characters of [A-Za-z0-9._-], not starting with -; at most 4 arguments.

On the server:

  • Server actions go through /usr/local/sbin/argus-helper (Python, run as root through sudo -n). The helper itself says it "is not a security boundary: <your user> has full sudo. It keeps Argus's buttons to known, logged actions."
  • Exceptions (they do not go through the helper):
    • Files: listing, previews and downloads run over SFTP as root (sudo -n /usr/lib/openssh/sftp-server). Uploads go to a temporary file over SFTP and are then put in place by the helper (file-commit); new folders are made by the helper (file-mkdir); downloads are recorded afterwards with note-file.
    • Terminal: a normal interactive shell as <your user> (pseudo-terminal xterm-256color). Nothing typed there is logged by Argus.
  • Long changes run as background systemd units (see "Background jobs" below).

Passwords and one-time secrets

  • Password dialog (shared): legend "Password", choices "Generate one and show it once" or "I'll type one" ("New password (12 characters or more)" and "Type it again"). Note shown: "The password goes to the server on its own channel. It is never put on a command line and never written to a log." The typed password (or the word generate) goes to the helper on stdin. The helper accepts 12 to 200 characters, no control characters. A generated password is 20 letters and digits with at least one digit, lower and upper case letter.
  • One-time display dialog: shows the value, warns "This is the only time it is shown. Copy it now; Argus clears the clipboard again after 30 seconds.", buttons Copy and Done.
  • Authenticator dialog (upload accounts): QR code, the key, five emergency codes; "This is the only time these are shown. Hand them over now; Argus clears the clipboard again after 30 seconds."; buttons Copy Key and Codes and Done.

Confirmations

Most changes open a confirmation dialog with a title, text, Cancel and a red button. Some ask you to type a word ("Type <word> to confirm") before the button works. Each one is listed under its button below.

The Activity log (and the helper's own log)

  • Every helper call is appended to /var/log/argus/actions.log (root, 0600) as one JSON line: time, session, action, arguments (or a readable summary the action records instead of raw hex), result (ok, refused: <why>, or failed: <type>). What the server sent back is never logged; passwords are never logged.
  • Arguments are cut to 64 characters (330 for file, mail, alias and quarantine actions). An action with unexpected arguments logs no arguments.
  • Session ids: a random 16-hex-character id per sign-in; jobs calling the helper use job-web-<6 digits>; the boot unit uses boot-mounts; the location timer uses geo-timer.
  • The Activity Log view (Activity Log) shows the last 300 entries.

Background jobs

  • start_job writes a script to /var/log/argus/jobs/<job>.sh (0700), logs to /var/log/argus/jobs/<job>.log (0600), and starts a transient unit argus-<job>.service with systemd-run (RuntimeMaxSec 3600 s; service updates 4 h). The log ends with ARGUS-RESULT: ok or ARGUS-RESULT: failed.
  • Jobs: updates, heph-rollback, heph-deploy, web, svc-update.
  • One change at a time: a lock file /var/log/argus/jobs/.lock. A new job (and reboot, upload-account changes, block list changes, staging a Hephaestus package, uploads into /opt/web) is refused with "another change is starting; try again in a moment", or "not now: the <job> job is still running", or "not now: the server is installing updates right now" (dpkg lock held).
  • On screen, a job box shows a heading ("Last update run: ", "Last rollback: ", "Last deploy: ", "Last web server change: ", "Last service update: ") with a pill Running, Finished, Failed or Interrupted, the last 40 log lines, and a final line ("■ Done: finished without errors.", "■ Stopped: it failed. The lines above say where.", or "■ Stopped before it finished (interrupted)."). While running it re-reads every 3 s (helper action job-status <job>).

App controls (sidebar foot) and header

  • Reload (tooltip "Redraw the screen; you stay signed in"): reloads the window. An open terminal session is closed on reload.
  • Restart (tooltip "Close and reopen Argus; sign in again afterwards"): confirm "Restart Argus?" / "Argus signs out, closes and opens again with any changes. Sign in again with your passphrase and a fresh code." / Restart Argus.
  • Exit (tooltip "Sign out and close Argus"): confirm "Exit Argus?" / "Argus signs out and closes." / Exit.
  • Header: Theme select ("Match Windows", "Light", "Dark"; remembered on this PC), Refresh (re-reads the dashboard status), Disconnect (closes the terminal and the connection and returns to the passphrase step).

The Pages

Sidebar order: Dashboard, Server, Websites, Mail, Accounts, Sign-In Attempts, Hephaestus, Backups, Files, Terminal, Activity Log.

Server

Services

Text: "Restarting a service stops it for a few seconds. Visitors to that site or service see an error while it starts again."

  • Table columns: Service, Version, Update Available, (actions).
  • Rows: running containers from the dashboard status (docker ps). Version and the update pill come from helper action service-updates (cached in /var/lib/argus/service-updates.json, re-checked when older than 6 hours). Pills: Up to Date, Update Available, Newer Version (Manual), Your Code (Hephaestus), Can't Check. Hovering a pill shows the detail. Footer: "Checked with each publisher <date>; checked again every 6 hours or with Check Now."
  • Button Restart (per row): confirm "Restart <name>?" / "<name> stops for a few seconds and starts again. Anything it serves shows an error meanwhile." / Restart. Helper action service-restart <name>: name must match a container name pattern and be running ("no running container by that name"), then docker restart -t 30 <name>.

Updates

Sub-heading System Packages

  • List from helper action updates-list: apt-get -s upgrade (it does not run apt-get update first, so it reflects the last package-list refresh), at most 60 packages. For each: description (apt-cache show), "<from> → <to> · <source>", and "What this update changes" (from apt-get changelog, entries newer than the installed version, cached in /var/cache/argus/changelogs and pruned after 60 days; "Change details are not available." otherwise).
  • Rating pills: High · security fix (from Debian security updates), High · marked urgent (maintainer urgency high, emergency or critical), Medium · time-sensitive fix (stable-updates), Low · routine, Not rated. Advice line: "Apply soon: ...", "Time-sensitive fixes. Apply when convenient, within a few days." or "Routine. These can wait for your next update round." If Docker or containerd is in the list: "This includes Docker. Installing it restarts every service on the server, mail included, for a minute or two."
  • Button Apply Updates (disabled when nothing is waiting): confirm "Apply Updates?" / "The waiting updates are installed now. Services they touch may restart briefly. [Docker sentence if included] If an update needs the server restarted, Argus says so and you choose when." / Apply Updates. Helper action updates-apply, job updates: apt-get -o DPkg::Lock::Timeout=600 update && apt-get -y -o DPkg::Lock::Timeout=600 -o Dpkg::Options::=--force-confdef -o Dpkg::Options::=--force-confold upgrade (non-interactive), then prints "A restart is needed to finish these updates." if /run/reboot-required exists. Refused while another job runs or apt is busy.

Sub-heading Service Updates, button Check Now (helper action service-updates refresh: checks every container with its publisher now).

  • What the check does (check_services): for each container, works out its kind:
    • mailcow containers: compares git describe --tags in /opt/mailcow-dockerized with the latest GitHub release of mailcow-dockerized.
    • hephaestus:local: shown as Your Code ("deploy new versions from the Hephaestus page").
    • images built on the server (a compose build: line, or bss-php:8.5 built by hand from /opt/web/php): checks whether the Dockerfile's base images have a patched build, and whether a newer base version exists.
    • ready-made images: compares the registry digest (Docker Hub or ghcr.io only) with the local one; pinned images (name:tag@sha256:...) are reported but changed by hand; newer tags of the same shape (same major or the next one) are reported as manual.
    • a container running an older copy of its image tag: "running an older copy of ...; restart it onto the current one".
  • Each item shows a pill (Update Available or Manual), the detail, a How to Update section (by-hand steps written by the helper), and, if Argus can apply it, a button:
    • Update Mail System (mailcow): confirm "Update the Mail System?" / "Argus takes a mail backup first, then runs mailcow's updater. Mail and webmail are unavailable for a few minutes. If the backup fails, nothing is updated." / Update Mail System.
    • Update (other services): confirm "Update <names>?" / "<detail>. It restarts for a few seconds; anything using it sees an error meanwhile." (plural wording for several) / Update.
  • Helper action service-update <container>|mailcow, job svc-update (4 h limit):
    • mailcow: 1/3 systemctl start mailcow-backup.service (if it fails: "The backup failed; nothing was updated."); 2/3 cd /opt/mailcow-dockerized; ./update.sh --force, run again if it exits 2 (it updated itself); 3/3 after 20 s, every mailcow container must be running. Clears the service cache.
    • pull: tags the running image argus-rollback/<name>:before-update, docker compose pull <svc>, docker compose up -d --no-deps --force-recreate <svc>, checks it runs.
    • rebuild: same, with docker compose build --pull <svc>.
    • rebuild-image (bss-php:8.5): tags it bss-php:before-update, docker build --pull -t bss-php:8.5 /opt/web/php, recreates every container that uses it, checks they run. On failure it prints the undo.
    • recreate: tags the running image argus-rollback/<name>:before-update, then recreates the container onto the current image.
  • Safeguards: "check for updates first" (no cache); "Argus has no update to apply for <name>; see How to Update"; the compose folder (from the container's labels, re-read live) must be a real root-owned folder under /opt, not writable by group or others, and not mailcow's ("that service can't be updated from here ..."). hephaestus-prod-migrate-1 is never offered.

Restart the Server

Text: "Everything on the server goes offline for about two minutes: websites, mail and Hephaestus. Argus disconnects and you sign in again afterwards."

  • Restart in One Minute: confirm "Restart the Server?" / "In one minute the server restarts. Websites, mail and Hephaestus are offline for about two minutes. You can cancel during that minute." / type restart / Restart in One Minute. Helper action reboot: under the change lock, shutdown -r +1 "Restart requested from Argus". Refused while a job runs or apt is busy. Afterwards: "The server restarts in one minute. Argus will lose its connection; sign in again in about three minutes."
  • Cancel the Restart (shown while a restart is scheduled): confirm "Cancel the Restart?" / "The scheduled restart is called off and the server keeps running." / Cancel the Restart. Helper action reboot-cancel: shutdown -c.
  • State line: "A restart is scheduled within the next minute." (from /run/systemd/shutdown/scheduled).

Websites

Sites

  • Table: Name, What It Is ("Website", "App on the server", "Redirect", "Other", with the folder, port or target underneath), Answering, Certificate, (actions).
  • Helper action sites-list: parses the site blocks in /opt/web/Caddyfile (and root lines in /opt/web/sites/<file>.caddy it imports); "Answering" is the HTTP code from curl --resolve <name>:443:127.0.0.1 https://<name>/ (for autoconfig.* names, /mail/config-v1.1.xml; for autodiscover.* names, /autodiscover/autodiscover.xml, because those mail-setup names have no front page and answer 404 there by design) (pill Not answering, "Error <code>" for 5xx, or the code); "Certificate" is days left via openssl s_client (red under 14 days, amber under 30, Unknown if unreadable).
  • Button Renew (per name): confirm "Get a New Certificate for <name>?" / "The current certificate is set aside (kept in /root/config-backups-argus) and the web server restarts; every site blips for a second or two. Caddy then asks Let's Encrypt for a new one, which takes up to a minute. Only needed if the certificate is wrong; Caddy renews on its own 30 days before expiry. Let's Encrypt allows about five new certificates per name per week, so do not repeat this many times. If no new certificate arrives within 90 seconds, the old one is put back." / Get a New Certificate. Helper action cert-renew <name>(hex), job web:
    • Refused if the name is not served, if /opt/web has edits not yet applied, or if no certificate folder is found.
    • Moves <caddy data folder>/caddy/certificates/<issuer>/<name> (the host folder bound to /data in bss-caddy) to /root/config-backups-argus/cert-<name>-<stamp>/<n>/, then runs the shared web job (below), testing every other name; step 5 waits up to 90 s for a certificate to be served for the name; if none, the old certificate folders are moved back.

Web Server Configuration

  • State line from sites-list: "Nothing has been applied through Argus yet. The first Apply keeps the configuration the web server is running now as the first good copy (only if the files have not been edited since it started).", or "The files have changed since the last apply (<stamp>). Check, then Apply.", or "The files match what was last applied (<stamp>)."
  • Help text: "To change it, edit the files in /opt/web on the Files page (the old version is kept). Then Check, and Apply. Apply restarts the web server: every site blips for a second or two. If a site that worked stops working, the last good configuration is put back by itself."
  • The configuration is /opt/web/Caddyfile, /opt/web/site-rules.caddy, /opt/web/docker-compose.yml and /opt/web/sites/*.caddy. /opt/web/caddy.env and /opt/web/agent-allow/allow.caddy are never shown.
  • Open /opt/web in Files: switches to Files at /opt/web.
  • Check: helper action caddy-check. Validates in a throwaway container: same image as bss-caddy, all its mounts read-only, --network none, --env-file /opt/web/caddy.env, an empty temporary /data/logs, caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile. Shows Valid or Not valid with the last 25 lines; values from caddy.env and addresses from the agent allow-list are replaced by "[hidden]", and lines naming HEPH_PROXY_SECRET or allow.caddy are dropped.
  • Apply Changes (disabled when nothing changed): confirm "Apply the Web Server Changes?" / "The configuration is checked first; if it does not pass, nothing is restarted and your edits stay as they are. Then the web server restarts (every site blips for a second or two) and every site is tested. If a site that worked before stops working, the last good configuration is put back by itself, and your edited files are kept in /var/lib/argus/caddy-history/failed-<time> so nothing is lost." / Apply. Helper action caddy-apply, job web.
    • The first time, it keeps the live configuration as the first good copy, but only if no file changed after bss-caddy last started; otherwise refused: "the files in /opt/web changed after the web server last started, so Argus cannot tell which configuration is live. Put the files back as they were (the Files page keeps copies) and try again, or ask for the first copy to be set up by hand".
    • Refused if "nothing has changed since the last apply".
  • Show the configuration files (expands): helper action caddy-show, read-only, each file as text.
  • Earlier configurations (expands): helper action caddy-history, up to 20 kept configurations, newest marked "(last applied)". Others have Roll Back to This: confirm "Roll the Web Server Configuration Back?" / "The configuration kept on <stamp> is put back, checked, and the web server restarts (every site blips). If a site that works in both would stop working, the current configuration is put back. Names added since then stop being served (their folders and files stay); the job lists them." / Roll Back. Helper action caddy-rollback <stamp>, job web. Refused if that configuration is not kept or /opt/web has unapplied edits. Only names present in both configurations are tested.

The shared web job (all of Apply, Roll Back, Renew, Add Site):

  1. "How each site answers now" (records each name's HTTP code).
  2. (Argus's own change, if any.) "Checking the configuration" (calls the helper's caddy-check).
  3. "Restarting the web server (every site blips for a second or two)": cd /opt/web; docker compose up -d caddy; docker restart bss-caddy.
  4. "Testing every site again": a site that answered under 400 and now gives 000 or 400 and up, or under 500 and now 500 and up, counts as broken.
  5. (Renew only: waiting for the certificate.)
  • On success: a copy goes to /var/lib/argus/caddy-history/<YYYYMMDD-HHMMSS>/; the 20 newest good copies and 10 newest failed copies are kept.
  • On failure after a change was made: the current files are copied to /var/lib/argus/caddy-history/failed-<stamp>/, the last good copy is put back, and the web server restarts. For Apply, if the check fails before any restart, nothing is put back and the edits stay.

Add a Site

  • Legend "What Should It Be?" with "A website (a folder of pages on the server)", "A redirect to another address", "An app running on the server (a local port)".
  • Fields: Domain (without www); for a redirect "Send visitors to (an https:// address)"; for an app "Local port the app listens on (for example 8090)".
  • Add Site: confirm "Add <domain>?" / "<domain> and www.<domain> become <what>. The web server restarts (every site blips). Nothing changes in DNS: Argus shows the records to add at your registrar, and the certificate arrives once they point here." / Add Site. Helper action site-add static|redirect|proxy <domain>(hex) [<target>(hex)], job web.
    • Website: makes /srv/<domain>/public (0755) with a "Coming soon" index.html if none, writes /opt/web/sites/<domain>.caddy (root, compression, security headers, dot-files answer 404, file server), adds a read-only mount of /srv/<domain>/public to /opt/web/docker-compose.yml (inserted before the site-rules.caddy mount line), and appends a block for <domain> plus a 308 redirect from www.<domain> to the Caddyfile.
    • Redirect: one block for both names, redir <target>{uri} 308. Target must be an https:// address.
    • App: reverse_proxy 127.0.0.1:<port> with compression; www. redirects. Port 1024 to 65535.
    • Refused: domain with www., domain already served, unapplied edits in /opt/web, no good configuration kept yet.
    • Afterwards the card shows the DNS records: A <domain> and A www.<domain> pointing to <server address>, and "No AAAA (IPv6) record: the server has no IPv6 address."
    • If the job puts the last good configuration back, the new /srv/<domain> folder is not removed (the job only restores the configuration files).

Mail

All mail data comes from mailcow's API at http://127.0.0.1:8080/api/v1/ on the server, using the API key in /opt/mailcow-dockerized/mailcow.conf (never printed). A change counts only if mailcow answers with an explicit success ("mailcow did not confirm the change; look again before retrying" otherwise; "mailcow refused it: ..." on an error). Helper action mail-overview loads the page: mailboxes, app passwords per mailbox, aliases, domains, queue, quarantine, and who has two-factor on (read-only query of the tfa table inside the mailcowdockerized-mysql-mailcow-1 container).

Mailboxes

  • Columns: Address (with name, Disabled pill), Used ("<used> of <limit> · <n>%"), Webmail Two-Factor (On, Off, Unknown), App Passwords (count), Last Sign-In (newest of IMAP, SMTP, POP3 and SSO sign-ins, or "never"), (actions).
  • Footer: "Mail apps use app passwords, one per device, so a lost phone is revoked without changing the main password. Two-factor is set up by each person in webmail; resetting it (for a lost phone) is done in mailcow's admin pages."
  • New Mailbox: asks "Full address (domains: ...)"     7. docker compose up -d; wait up to 2 minutes for healthy.
    8. Record the commit in /var/lib/argus/heph-deployed, remove the staged copy, run scripts/verify.sh as in the rollback.

Doing It by Hand

Running the helper yourself

The helper works without Argus. From an SSH session as <your user>:

hex() { printf '%s' "$1" | od -An -tx1 -v | tr -d ' \n'; }
sudo /usr/local/sbin/argus-helper --session by-hand-01 <action> [args]
  • The session id must be 8 to 64 letters, digits or hyphens. The call is logged like Argus's.
  • Arguments marked (hex) above must be hex-encoded, lowercase (the hex function above does that).
  • Password actions read stdin: printf '%s' generate | sudo /usr/local/sbin/argus-helper --session by-hand-01 mailbox-password $(hex user@example.com). Output is JSON on stdout; a generated password or authenticator secret is printed to your terminal.
  • Exit codes: 0 ok, 3 refused (reason on stderr), 2 bad usage or arguments, 1 failed.
  • Audit note: the helper records the calling SSH session's address as one of yours for 180 days; running it from a long-lived tmux shell can record a stale address.
  • Job progress: sudo tail -40 /var/log/argus/jobs/<job>.log; systemctl status argus-<job>.service.

The raw commands below are taken from the helper's code. Anything not derived from the code is marked (uncertain).

Server

  • Restart a container: sudo docker restart -t 30 <name>

  • Service updates: each item's How to Update gives the by-hand steps. From the code:
    • mailcow: cd /opt/mailcow-dockerized && sudo ./update.sh --check, then sudo ./update.sh (Argus first runs sudo systemctl start mailcow-backup.service and uses ./update.sh --force, repeated once if it exits 2).
    • patched image: cd <compose folder> && sudo docker compose pull <svc> && sudo docker compose up -d --no-deps <svc>

    • Major database versions (PostgreSQL, MySQL, MariaDB): the How to Update steps cover dump, new volume or in-place upgrade, and undo; Argus never does these itself.

Recovery

Locked out by the block list

  • Your known admin networks are accepted ahead of the drops, and blocks overlapping them, the server, its gateways or name servers are refused. A risk remains if you later sign in from a new address inside a blocked network.
  • The way back in, from the Block confirmation text: use the cloud provider's console and run sudo nft destroy table inet argus && sudo systemctl disable argus-blocklist.service, then unblock the network in Argus, then sudo systemctl enable argus-blocklist.service.
  • nft destroy table alone lasts only until the next boot or nftables reload, which is why the service must be disabled too; and your cloud provider's serial console needs an account that can sign in with a password (an SSH-key-only setup usually has none), so the console sign-in has to be tested once beforehand (a local password-capable user, or your provider's run-command feature). Do this once now, not when you are locked out: sign in at your cloud provider's console and make sure you can get a shell there.

SSH and PAM changes from accounts-setup.sh

  • The script prints the undo command to use if your sign-in fails: cp -a /var/backups/argus-setup/pam-sshd.pre-argus-<stamp> /etc/pam.d/sshd. Root's own sign-in is key-only and never uses the authenticator, so a root session stays usable to undo it.
  • If sshd -t rejects the settings, the script puts the PAM file back and removes the two Argus sshd files itself.
  • /etc/fstab before quotas: /var/backups/argus-setup/fstab.pre-quota-<stamp> (put back automatically if the remount fails).
  • 04-argus-loglevel.conf is removed automatically if sshd -t rejects it.

Hephaestus

  • Rollback tags: a deploy keeps the live image as hephaestus:pre-<live commit> (or pre-argus-<stamp>; a stamp is appended rather than move an existing tag). A rollback keeps the live image as pre-argus-<stamp>, so it can itself be undone; only the three newest pre-argus- tags are kept.
  • Automatic revert: a rollback that does not start or is not healthy in 2 minutes puts the previous image back; a deploy that fails at copy, build, migrate or start restores the source backup and the kept image.
  • Database migrations are never undone; "columns added by newer versions stay, which does no harm."
  • Before every deploy: source backup in /root/config-backups-argus/hephaestus-pre-<commit>-<stamp> and database dump /root/heph-pre-<commit>-<stamp>.dump.
  • If the server checks fail after a deploy or rollback, the new version stays live; roll back from the page.

Web server

  • Every good apply is kept in /var/lib/argus/caddy-history/<stamp>; Earlier configurations can put one back.
  • After a failed change, the files as they were go to /var/lib/argus/caddy-history/failed-<stamp> before the last good copy is restored.
  • Renew: the old certificate is moved back if no new one arrives within 90 s; the set-aside copy stays in /root/config-backups-argus/cert-<name>-<stamp>.
  • Let's Encrypt limit noted in the Renew text: about five new certificates per name per week.

Services and updates

  • Service updates keep the previous image as argus-rollback/<name>:before-update (pull, rebuild, recreate) or bss-php:before-update (rebuild of bss-php:8.5); for bss-php the job prints the undo ("docker tag bss-php:before-update bss-php:8.5, then restart the same containers"). For the other kinds, the code gives no undo command.
  • A mailcow update starts only after a successful mail backup.
  • Major database upgrades: the How to Update steps include taking a dump first and how to undo.

Files and accounts

  • Overwritten files: /var/backups/argus/<date>/<time><path>.
  • A deleted upload account's own folder: /var/backups/argus/account-<name>-<stamp> (30 days, per the tmpfiles rule the helper refers to); files it put in a shared folder stay, owned by root.
  • Lost phone (upload account): New Authenticator Code, or one of the five emergency codes. Lost phone (Hephaestus user): Reset Two-Factor. Lost phone (mailbox): mailcow admin pages. The code does not cover a lost authenticator for your own <your user> sign-in.
  • The last <your user> key can't be removed.
  • Shared folders not reconnected after a boot show Not Connected; acct-mount-all reconnects them (it runs at boot).

Connection

  • A lost connection needs Disconnect and a fresh sign-in (a new code).
  • A scheduled server restart can be cancelled during its minute with Cancel the Restart.
